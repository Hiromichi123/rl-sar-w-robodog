1协议总览

本协议定义外部上位机（浏览器 Web UI、ROS2 节点、CLI 工具）与机器人主控程序 rl_real_JXG 之间的全部通信通道。系统同时支持两种传输层：

  • WebSocket（内嵌 WebBridge，端口 8088）：浏览器直连，JSON 帧格式 {"type":"<通道>","data":<payload>}，cmd_vel 使用扁平字段 vx/vy/yaw
  • ROS2 Topic（DDS）：ROS 节点间通信用 std_msgs/String（JSON payload）和 geometry_msgs/Twist（cmd_vel）

两种传输层共用同一套 payload 格式和命令处理逻辑，后端在合成层统一出口（EmitCommandState）双发 ROS Topic + WebSocket。

设计原则：
  • Web 独占仲裁：Web 非零速度获取独占锁（1.0s 窗口），期间 ROS cmd_vel 被丢弃。松手断联超时自动归零，随后 ROS 接管。
  • 命令串行：同一时刻仅跟踪一条 pending 命令，新命令取代旧跟踪。
  • 抗丢包 Burst：常规 FSM 命令连发 3 帧（间隔 500ms，总计 1.0s），后端用 seq + 1.5s 窗口 去重。
  • 断联归零：cmd_vel 超过 0.5s 无新帧 → 自动归零停车（Web 与 ROS 共用一份计时器）。

3速度指令 (cmd_vel)

3.1 帧格式

WebSocket 帧使用扁平字段（非标准 data 包裹）：

{
  "type": "cmd_vel",
  "vx": 0.50,     // 线速度 X (m/s)，前进为正
  "vy": 0.00,     // 线速度 Y (m/s)，左移为正
  "yaw": 0.30     // 角速度 Z (rad/s)，左转为正
}

ROS2 话题使用标准 geometry_msgs/Twist：linear.x = vx, linear.y = vy, angular.z = yaw。

3.2 发送节奏：20Hz 持续发布 + 尾帧停发

阶段行为频率
非零速度启动 20Hz keep-alive 定时器，每 50ms 发一帧20Hz
归零（非零→零跳变）追加 5 帧零速度尾帧后停止定时器（避免真机收到一次零后又收到非零 keepalive）20Hz × 5
已是零且尾帧发完停止定时器，不再发帧（省 CPU）—
断联超时后端 0.5s 无新帧 → 自动归零（Web 与 ROS 共用计时器）—

3.3 死区

所有速度分量在写入前经过死区过滤：|v| < 0.05 → 0。消除指令源零位漂移，Web 与 ROS 两链路共用。

3.4 Web 独占仲裁

Web 独占机制：Web 链路的非零速度获取独占锁（保持窗口 1.0s），期间 ROS /rl_real/cmd_vel 帧被丢弃并回复 "cmd_vel ignored: web exclusive active"。Web 松手后独占锁自然过期，ROS 恢复接管。零速尾帧不续期独占，但仍写入以保证停车。

4.3 Burst 机制（"开始发送 → 发送中 → 发送结束"）

常规 FSM 命令采用 3 帧 Burst 发送，对齐旧 CLI --times 3 --rate 2：

第 1 帧（立即发）
→ 500ms 间隔 →
第 2 帧
→ 500ms 间隔 →
第 3 帧 → Burst 结束
  • 总持续 1.0s（3 帧 × 500ms 间隔）
  • 同一时刻新命令进来会 cancel 上一个未发完的 Burst（避免叠发）
  • 单发命令（zero / check_standing / probe_*）不进入 Burst，只发 1 帧
  • 带序号命令去重：seq + 1.5s 窗口 内同 seq 重复帧丢弃
设计原因：FSM 状态切换命令（站立/趴下/进 RL）若丢一帧会导致机器人卡在中间态。3 帧 Burst 以 500ms 间隔抗丢包，后端去重窗口 1.5s 容忍 Burst 内同 seq 重复。置零类命令不 Burst 是因为执行耗时约 2s，叠发会打断正在进行的逐台写零流程。

5命令状态生命周期 (cmd_state)

这是你提到的"开始发送 → 发送中 → 发送结束"的核心协议。每条命令从受理到终态，后端通过 cmd_state 通道逐步回报状态。

5.1 状态码

codephase含义触发时机
0RECEIVED已收到命令受理瞬间（去重通过后立即发）
1EXECUTING执行中FSM 开始切换/动作开始
2DONE完成进入目标态且稳态 + 满足最小执行时长
3FAILED超时失败超时未进入目标态
4REJECTED拒绝门禁未通过（CAN/站姿/卧姿/探针）

5.2 帧格式

{
  "type": "cmd_state",
  "data": {
    "seq": 1,                    // 命令序号（ws_demo 带序号 >0；ROS/Web 页面 seq=0）
    "cmd": "getup",              // 原始命令字符串
    "code": 1,                   // 状态码 0-4
    "phase": "EXECUTING",        // 状态名（冗余字段，方便解析）
    "target": "RLFSMStateGetUp", // 目标 FSM 状态名（无目标时为 null）
    "state": "RLFSMStatePassive", // 当前 FSM 状态名
    "elapsed_ms": 340            // 从受理到本帧耗时（毫秒）
  }
}

5.4 跟踪机制 (TrackFsmCommand)

后端为每条命令创建 PendingCommand 跟踪对象，在控制环（200Hz）中以 UpdatePendingCommand 轮询：

  • EXECUTING：首次轮询时发（executing_sent 标志防重）
  • DONE：当前 FSM 状态 == 目标态 && behavior_settled && 经过 min_sec 最小时长
  • FAILED：超过 timeout_sec 未到位
  • REJECTED：门禁检查未通过，立即发（不经 EXECUTING）
seq=0 命令同样跟踪：ROS 话题和 Web 页面的命令 seq=0，合成层靠 posture/settled 边沿产出 DONE/FAILED。SafeHold 状态下进行中的命令标记为 FAILED。

5.5 各命令的 cmd_state 生命周期路径

关键：所有命令无条件发 RECEIVED（code=0）。但此后并非每条命令都走完整 RECEIVED → EXECUTING → DONE/FAILED/REJECTED 链——按命令类型分为 5 类：

A 类：完整生命周期（RECEIVED → EXECUTING → DONE / FAILED / REJECTED）

通过 TrackFsmCommand 创建 PendingCommand 跟踪对象，在 200Hz 控制环中轮询产出终态：

命令目标态超时说明
getupRLFSMStateGetUp6.0s站立插值完成
getdownRLFSMStatePassive8.0s趴下插值 2s + 余量后回 passive
locomotionRLFSMStateRLLocomotion5.0s进入强化学习
passiveRLFSMStatePassive5.0s释放关节

这 4 条命令才有 FAILED（超时未到位）和 REJECTED（门禁未通过）。

B 类：同步两步（RECEIVED → EXECUTING → DONE / REJECTED）

同步执行，立即出结果，无 FAILED（不跟踪超时）：

命令终态条件
check_stand / check卧姿校验通过 → DONE；未通过 → REJECTED
check_standing站姿校验通过 → DONE；未通过 → REJECTED

C 类：异步无终态（RECEIVED → EXECUTING，无 DONE/FAILED/REJECTED）

注意：以下命令只发 RECEIVED + EXECUTING 两帧，之后异步线程通过 notify 通道逐台推送结果，cmd_state 通道不会发终态。上层需监听 notify 的 type:"probe" 消息判断完成。
命令结果通道说明
probe_motors / probenotify (probe: start/result × 16/done)16 台并行探针，约 2s
probe_motor <id> / probe <id>notify (probe: single)单台探针（无效 ID → REJECTED）
probe_leg FL/FR/RL/RRnotify (probe: legdone)分腿探针
sys_reboot—（进程死亡）1s 后系统重启，来不及发终态
sys_poweroff—（进程死亡）1s 后关机，来不及发终态

D 类：立即完成（RECEIVED → DONE，跳过 EXECUTING）

同步执行且必定成功（无 FAILED/REJECTED 路径）：

命令说明
zero / zero_all16 台全部置零（仅 Passive 允许，否则 REJECTED）
zero_motor <0-15>单台置零（无效 ID → REJECTED）
zero_motors 0,2,7批量置零（解析错误 → REJECTED）
rl_block / block退出 RL → SafeHold
vel_stop / hold速度清零
posture / pose即时广播姿态帧

E 类：仅拒绝（RECEIVED → REJECTED）

8Hz 机器人→上位机

{
  "type": "posture",
  "data": {
    "posture": "standing",          // lying/standing/locomotion/transition/unknown
    "fsm": "RLFSMStateGetUp",       // FSM 原始状态名
    "settled": true,                // 当前态是否稳态（插值完成/策略接管）
    "motors_ready": true,           // 电机零位检查通过

7通知与事件 (notify)

机器人→上位机 事件驱动

机器人主动推送的事件通知（错误/警告/信息/探针结果等），带去重/重试机制。上位机收到后应回复 notify_ack。

{
  "type": "notify",
  "data": {
    "id": 5,                    // 通知序号（递增）
    "type": "error",            // info/warning/error/success/probe/note
    "content": "CAN 反馈超时，已立即退出强化学习",
    "timestamp": 1286.523       // 单调时钟秒
  }
}

notify_ack（上位机→机器人）

{"type": "notify_ack", "data": "{\"id\":5,\"ok\":true}"}

未 ack 的通知会重试推送（约 2Hz），直到 ack 或超时清除。

8校验通道

8.1 check_stand — 卧姿校验

上位机发 {"type":"check_stand","data":"check"}，机器人执行电机零位+IMU 检查后回报：

{"type": "check_stand_result", "data": "{\"at_stand\":true,\"joints_ready\":true,...}"}

结果通过后解锁起立门禁。趴下后记录作废，每次起立前需重新校验。

8.2 check_standing — 站姿期望值校验

上位机发 {"type":"check_stand","data":"check_standing"}，机器人检查 12 腿关节是否在站立期望构型容差内（±0.30rad），回报：

{
  "type": "check_standing_result",
  "data": {
    "at_stand": true,
    "joints_ready": true,
    "imu_ready": true,
    "can_ready": true,
    "worst_err": 0.012,
    "worst_joint": 3,
    "tol": 0.3,
    "reason": "",
    "posture": { ... }            // 内嵌完整 posture 帧
  }
}

8.3 zero_result — 置零结果

置零命令（zero / zero_motor / zero_motors）执行后，通过 feedback 通道回报结构化结果：

{"type": "feedback", "data": "zero_result {\"zeroed\":[0,1,2,3],\"failed\":[7]}"}

8.4 探针 (probe)

探针结果通过 notify 通道推送，type 为 probe：

{"type": "notify", "data": {"id":1,"type":"probe","content":"result m0 FL_hip_joint ok"}}

探针完成后："done 2"（失败台数），"single m0 FL_hip_joint ok"（单台），"legdone 0 0"（分腿完成）。
